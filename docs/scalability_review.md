# مراجعة قابلية التوسع والاستقرار

## النطاق

هذه المراجعة تغطي تطبيق Flutter المحلي الحالي. مصادر البيانات في النسخة الحالية
Mock/In-memory ولا يوجد HTTP client أو Backend أو قاعدة بيانات دائمة، لذلك لا توجد
طلبات شبكة فعلية يمكن قياس Timeout أو إلغاؤها الآن.

## نقاط الضعف التي عولجت

| نقطة الضعف | الأثر عند نمو البيانات | التحسين المنفذ |
| --- | --- | --- |
| اشتراك `HomeViewModel.load()` قابل للتكرار | اشتراكات مكررة وإعادة بناء متكررة | أصبح التحميل idempotent، وتبقى الاشتراكات ملغاة في `dispose`. |
| أقسام Home كانت تفلتر قائمة الفنادق في كل `build` | عمل متكرر مع آلاف الفنادق | تُحسب `featured` و`popular` و`recommended` عند وصول البيانات فقط، وتُحد إلى 10 بطاقات للصفحة الرئيسية. |
| البحث يطلق عملية لكل حرف | ضغط غير لازم عند ربط API وتأخر عرض النتائج | أضيف debounce مدته 250ms، ورقم طلب يمنع نتيجة قديمة من استبدال نتيجة أحدث. |
| نتائج البحث تبني جميع البطاقات | ذاكرة/Jank مع آلاف النتائج | استبدلت بـ `ListView.builder`. |
| صفوف Explore الأفقية تبني كل بطاقاتها | إنشاء Widgets غير مرئية | استبدلت بـ `ListView.builder`. |
| اختيار الغرفة ينشئ `Future` جلب الفندق خلال `build` | إعادة تحميل الفندق بعد كل اختيار غرفة | يخزّن `RoomSelectionPage` الـFuture مرة واحدة في `initState`. |
| صور البطاقات تستخدم الصورة الأصلية | ضغط ذاكرة كبير عند تمرير قوائم طويلة | أضيفت أبعاد cache للصور المصغرة وحد أقصى عالمي لذاكرة image cache: 250 صورة أو 60MiB. |

## إدارة الحالة ودورة الحياة

- `HomeViewModel` و`ExploreViewModel` يلغيان اشتراكات Stream في `dispose`.
- Debounce البحث يُلغى في `dispose`، وتُهمل الاستجابات المتأخرة عبر request version.
- المسودات الخاصة بالحجز تبقى في `BookingFlowCoordinator` فقط خلال تدفق الحجز، ثم تُحرر بعد التأكيد أو الإلغاء.
- واجهات البيانات موجودة خلف Repository contracts، ولذلك يمكن استبدال مصادر Mock دون تغيير Widgets.

## المخاطر المتبقية

1. لا توجد شبكة في هذه النسخة؛ لا يمكن إلغاء `Future` عام في Dart إلا إذا كان عميل الشبكة يدعم cancellation صراحةً.
2. البحث والفرز يتمان داخل `MockSearchRepository` على isolate الواجهة. هذا مناسب للبيانات المحلية الصغيرة الحالية، لكنه يجب أن ينتقل إلى API مفهرس أو isolate عند معالجة آلاف السجلات محليًا.
3. `MockHotelRepository` هو مصدر ذاكرة لجلسة التطبيق فقط؛ لا توجد سياسة TTL أو invalidation أو تخزين Offline فعلي.
4. تفاصيل الفندق وقائمة الغرف تستخدمان قوائم قصيرة عادةً، لكنها تحتاج Slivers إذا أصبح عدد الغرف أو الفنادق المشابهة كبيرًا بصورة غير معتادة.

## توصيات Backend للإنتاج

1. استخدم API مُجزأ pagination/cursor لكل قوائم الفنادق والصور والحجوزات، مع حد حجم صفحة واضح.
2. اجعل البحث والفرز والفلترة على الخادم بفهارس للمدينة والمحافظة والسعر والتقييم، ولا تنقل آلاف السجلات إلى الهاتف للفلترة.
3. أضف طبقة Remote Data Source قابلة للإلغاء (مثل `AbortableRequest` أو client يدعم cancellation) ومرّر cancellation token من ViewModel عند `dispose`.
4. طبّق timeout لكل فئة طلب، retry محدودًا للطلبات idempotent فقط مع exponential backoff وjitter، ورسائل خطأ آمنة للمستخدم.
5. استخدم ETag/Cache-Control وذاكرة/قرص cache بمدة TTL، مع stale-while-revalidate وصور CDN بأحجام responsive.
6. اجعل تأكيد الحجز idempotent بمفتاح طلب، واستخدم معاملات وقفل المخزون على الخادم؛ لا تعتمد على عدد الغرف التجريبي في العميل.
7. أضف observability: tracing، معدلات فشل، زمن p95/p99، ومراقبة crash/jank من دون تسجيل بيانات الضيوف أو الرموز السرية.
